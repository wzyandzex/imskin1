# 输入法皮肤智能体系统 — 架构设计文档

## 0. 设计前提与硬性原则

本方案确认的两条产品原则，贯穿以下所有模块设计，不作为”如果时间允许”的加分项，而是作为约束条件：

1. **效果优先于工作量**：任何环节，如果更深入的方案设计、更多的代码能让最终生成的皮肤质量和效果更好，就不能因为要降低工作量而选择最小方案。这直接否决了”生成一张静态效果图当作皮肤”或”预览用截图轮播糊弄”这类捷径。
1. **前端平台设计以用户真实体验为最终依据**，不以实现简便为依据。预览必须是”像日常使用输入法一样”的真实交互，而不是设计稿展示。

基于第一轮调研确认的关键事实（详见 `01_platform_formats.md`），系统采用 **Plan A**：

- **搜狗 PC 皮肤（.ssf）**：格式公开、可编程直接生成，端到端全自动，零人工干预。
- **百度 PC 皮肤（.bps）**：无公开写规范，走”标准化工程文件 + 自动化驱动官方皮肤编辑器完成最终导出”的路径；此路径存在一个未验证的技术假设（GUI 自动化的可行性与稳定性），已作为显式风险项管理，不隐藏在乐观假设里。

## 1. 系统总览

### 1.1 用户旅程（端到端）

```
① 输入采集
   ├─ 一段模糊/清晰的文字想法
   ├─ （可选）一张参考图
   ├─ （可选）一段参考视频
   └─ （模糊时）提示词优化对话，把想法收敛成可执行的设计需求
        ↓
② 设计意图生成（Design Brief）
   智能体把"想法 + 参考素材"转成结构化设计简报：
   风格关键词、配色方案、材质/纹理方向、布局取舍、动效意向、
   目标情绪（如"清冷极简" vs "复古国潮"）
        ↓
③ 视觉资产生成
   背景图、按键前景/背景九宫格切图、状态栏图标、候选栏样式、
   动效帧（apng）—— 按两个目标平台的资产规格分别产出
        ↓
④ 双出口打包
   ├─ 搜狗：直接组装 skin.ini + 切图 → .ssf（全自动）
   └─ 百度：组装标准化工程文件 → 驱动官方编辑器 → .bps（自动化，含降级路径）
        ↓
⑤ 实时预览（核心体验）
   用户在平台内直接"打字体验"这版皮肤 —— 见 03_preview_engine.md
        ↓
⑥ 多轮反馈迭代
   用户用自然语言指出问题（"候选词字太小""按键太方了""这个背景太亮"）
   智能体定位到具体的设计参数/资产，做针对性重生成，而不是整体推倒重来
        ↓
⑦ 定稿导出
   用户确认后，导出两个平台的正式安装包 + 安装引导
```

│  ├─ 参考图/参考视频解析（风格提取、关键帧提取、配色提取）              │
│  └─ 资产版本库（每版皮肤的全部产出物可追溯、可回滚）                  │
├─────────────────────────────────────────────────────────────┤
│  数据与状态层                                                   │

# 1. 平台格式规格与生成策略

## 1.1 搜狗输入法 PC 皮肤（.ssf）—— 全自动生成路径

### 已确认事实

- 容器：标准 zip，重命名为 `.ssf` 即为完整皮肤文件；反之亦可将 `.ssf` 改名 `.zip` 解压查看/修改。
- 内容构成：一个 `skin.ini` 配置文件 + 若干 `.png`/`.apng` 图片资源。
- 安装机制：双击后拷贝到安装目录 `allskin` 文件夹并解压到 `skin` 文件夹，随后出现在皮肤列表中。
- 官方提供”设计 - 切图 - 生成”标准流程与皮肤编辑器，说明存在明确的切图规格表（候选栏、拼音区、云候选区、键盘大背景、9键/26键、弹泡等元素）。

### 生成策略：直接编程组装，不经过官方 GUI

因为格式全公开，**资产生成 Agent + 参数装配 Agent** 可以完全绕开搜狗官方编辑器，直接：

1. 按官方切图规格（背景图、按键前景/背景、状态栏、候选栏、弹泡动画等）生成/切割各分辨率资源图。
1. 程序化写出 `skin.ini`，覆盖其全部可控节区，包括（需在验证阶段拿到官方最新版《制作教程》PDF 逐项核对，当前已知需要覆盖的类别）：
- 输入窗口背景与九宫格拉伸区（横排/竖排两套）
- 候选词区域：字体、字号、颜色（含选中态/非选中态/序号）
- 拼音串显示区域位置与样式
- 状态栏图标集（中英切换、全半角、软键盘等各状态图标）
- 按键背景与前景（若支持虚拟键盘皮肤）
- apng 动效帧序列与帧率
- 版本兼容标记（如格式中存在 min/max 版本字段，需写入以避免新旧客户端渲染错位）
1. 按目录结构（`skin.ini` 位于根目录，图片资源在约定子目录）打包为 zip，重命名为 `.ssf`。

### 为什么不用官方编辑器

官方编辑器是给人手动操作的 GUI 工具，没有已知的命令行接口。既然格式本身透明可写，绕开 GUI 直接生成比自动化一个人机交互工具更可靠、更快、更不容易因为编辑器界面变化而失效。**这是”效果优先”与”工程稳健性”两者一致的情况**——不是走捷径，是这条路径本来就是更优解。

### 需要提前做的验证（非阻塞，但应尽早）

- 找到搜狗官方最新《皮肤制作教程》完整 PDF，逐字段核对 `skin.ini` 语法（教程 PDF 已在搜索结果中定位到 URL，需要完整抓取解析）。
- 用生成的 `.ssf` 在真实搜狗客户端（Windows）测试安装与显示，建立”生成 → 真机验证”的自动化回归测试集，覆盖不同分辨率/DPI。
- 收集实际的官方皮肤样本（下载几十个真实上架皮肤，改名解压研究 `skin.ini` 全量字段），作为参数装配 Agent 的”参数字典”来源，比只读教程文档更可靠、更全。

## 1.2 百度输入法 PC 皮肤（.bps）—— 自动化驱动官方编辑器路径

### 已确认事实

- 容器格式：官方声明”不可通过更改后缀名解压等方式获取原始图片”，但也有实操记录显示可以用解压软件直接打开 `.bps` 文件获取素材文件夹。二者不矛盾的合理解释：**官方在文档层面不背书这种用法（防止有人绕过编辑器盗图/破解版权保护机制），但容器本身大概率仍是 zip 家族**，只是编辑器在导出时可能附加了签名、校验、ID 编码等编辑器私有元数据。
- 内容构成：png/apng 图片 + 配置信息。
- 没有公开的配置文件语法规范（不像搜狗的 `skin.ini` 有官方文档）。
- 官方标准制作流程固定为四步：**设计效果图 → 按素材要求切图 → 用皮肤编辑器导入切图并编辑 → 编辑器内检错 → 生成皮肤文件**。这四步全部在官方 GUI（BDPYSkinEditor）内完成。
- 安装机制：双击 `.bps` 拷贝到 `skin` 目录并更新皮肤列表，与搜狗类似。

### 生成策略：不逆向猜格式，改为”自动化操作官方编辑器”

**关键判断**：既然百度没有公开规范，纯逆向工程写一个”假的 bps 生成器”是一种自欺欺人的最小方案——即使某个版本能通过，客户端可能做校验（编辑器可能内嵌签名/哈希），编辑器一旦升级格式也可能变化，我们完全没有官方对齐渠道去跟踪这些变化。**这不是”效果优先”该选的路**，效果优先选的是能长期稳定产出正确安装包的路径，而不是短期能跑但随时会碎的路径。

因此百度出口采用：

1. **参数装配 Agent** 产出一份”标准化设计工程”：按官方切图规格（状态栏、横排窗口、竖排窗口、九宫格拉伸标注、按键各状态图 [标准/悬停/按下]、字体颜色参数等）组织好的完整素材包 + 参数清单（JSON，作为自动化脚本的输入）。
1. **编辑器自动化驱动层**：在托管的 Windows（或 Wine）沙箱环境中，用 UI 自动化技术（如 pywinauto / AutoHotkey / Windows UI Automation API）驱动 BDPYSkinEditor：
- 新建工程 → 逐项导入背景图/按钮各状态图 → 设置九宫格拉伸区坐标 → 设置字体颜色参数 → 触发”检错” → 读取检错结果 → 触发”生成/导出” → 抓取产出的 `.bps` 文件。
- 所有点击坐标/控件定位优先用控件 ID/自动化树（Accessibility Tree）而非像素坐标，以降低界面细微变化带来的脆弱性。
1. 若 GUI 自动化在某个环节失败（例如某个对话框行为无法自动化），系统应能明确报告”卡在哪一步”，而不是静默失败产出一个假文件。

### 已识别的核心技术风险（未验证，需要专门的技术 Spike，详见 `06_risks_and_validation.md`）

- 编辑器是否需要账号登录/联网校验才能导出（会阻断无人值守自动化）。
- 编辑器窗口/控件是否有稳定的可访问性标识，还是纯像素级绘制（后者会让自动化非常脆弱）。
- 官方下载渠道的编辑器二进制来源需要正式核实（不能依赖论坛/网盘镜像，需要找百度官方页面的直接下载，或与百度方面确认合作渠道）。
- 编辑器版本升级频率与我们自动化脚本的维护成本对应关系。

### 降级路径（Path A-fallback，不是另立方案，是同一方案的容错设计）

若纯无人值守自动化在某些边界情况下不稳定：

- 保留同一套自动化流程，但允许在检错失败或异常状态时，把当前工程状态推送到一个人工监督队列，由人工在编辑器里点一下”确认导出”（其余步骤仍是自动化的），系统记录下这次人工介入的原因，用于持续缩小需要人工介入的场景范围。
- 这不改变用户侧体验（用户仍然只是在等一个”生成中”的状态，可能多等几十秒），只是后端在少数情况下多一道人工确认关卡，作为可用性兜底，而不是把限制转嫁给用户。

## 1.3 两个出口的资产生产是否可以复用

虽然容器和配置层完全不同，**视觉设计阶段（配色、构图、风格、动效意向）应该是共享的**——同一版皮肤在两个平台上应该看起来是”同一个设计”，只是分别按各自的切图规格重新精确切图和适配控件坐标系。

资产生成 Agent 的产出应分两层：

1. **设计层产出**（平台无关）：主视觉稿、色板、字体方案、动效脚本 —— 一份。
1. **平台适配层产出**（各自独立）：按搜狗规格的切图集 + 按百度规格的切图集 —— 分别生成，允许有平台特定的细节调整（比如百度的九宫格拉伸区坐标系可能和搜狗的定义方式不同，需要各自独立计算）。

这样反馈迭代时，如果用户说”整体配色再冷一点”，两个平台同步重新走一遍资产适配；如果用户说”搜狗这边候选词字体太小”（平台特定问题），只重新跑搜狗那条适配管线，不影响百度端已经生成好的版本——避免不必要的重新生成，这也是”效果优先”的另一层含义：**精准定位问题、不做无谓的整体重跑**，重跑越少，用户等待时间越短，也越不容易在没问题的地方引入新问题。

# 2. 智能体编排管线

## 2.1 设计原则

每个 Agent 的输出必须是**结构化、可追溯、可单独重跑**的，而不是”一个大模型端到端吐出最终文件”。理由：

- 用户反馈往往是局部的（“候选词字体太小”），如果整个管线是一个黑盒端到端生成，定位问题和局部重跑就做不到，只能整体重来——这既慢又容易把用户已经满意的部分改坏。
- 每一层的中间产物（设计简报、视觉规格、资产清单）都应该允许用户在 UI 上直接查看甚至编辑，这比”猜用户想要什么”更可靠。

## 2.2 管线详解

### Agent 1：意图理解（Idea → Design Brief）

**输入**：用户文字描述（可能模糊）+ 参考图（可选）+ 参考视频（可选）

**处理**：

- 若文字描述信息量不足（判定标准：缺少风格、配色、情绪基调三者中任意两项以上的明确指向），触发**提示词优化对话**：智能体主动追问，但遵循”一次最多问一个关键问题”的克制原则，优先根据已给的参考图/视频自行推断合理默认值，而不是连续追问打断体验。
- 若提供参考图：跑视觉特征提取（主色调、构图密度、材质倾向如玻璃拟态/扁平/拟物、圆角程度、字重倾向）。
- 若提供参考视频：抽取关键帧（场景切换点/色彩变化点），同样跑视觉特征提取；如果视频包含动效意向（比如用户想要”输入时有粒子效果”），需要识别出这类**行为性需求**而非纯视觉需求，路由给动效设计而非静态资产设计。

**输出**（结构化 Design Brief，示例字段）：

```json
{
  "style_keywords": ["国潮", "水墨", "留白"],
  "color_palette": {"primary": "#...", "accent": "#...", "background": "#..."},
  "mood": "沉静内敛",
  "material_direction": "哑光纸质感，非玻璃拟态",
  "corner_radius_preference": "large",
  "motion_intent": ["候选词切换有淡入效果"],
  "reference_assets": {"image": "...", "video_keyframes": ["..."]},
  "ambiguity_resolved_by": ["用户回答的追问", "参考图推断"]
}
```

这份简报要**展示给用户确认**（前端有一步”设计意图确认”卡片），避免智能体基于误解跑完整条流水线才发现方向错了——这是效果优先原则下必须要有的一步，省掉它short-term省事，long-term是用户体验的重大减分（辛辛苦苦生成一版结果发现方向就错了，比多问一次confirm的成本高得多）。

### Agent 2：视觉设计（Design Brief → Visual Spec）

把设计简报转成”可执行的视觉规格”：具体到每个 UI 元素（候选栏、按键、状态栏、拼音条）应该长什么样、用什么配色层级、圆角/阴影/描边参数、字体族与字重、动效的具体时序曲线。

这一步产出**设计稿**（可以是实际渲染出的高保真效果图，让用户在生成真实切图之前就能看到大致方向），也产出结构化的**设计 token**（颜色变量、间距变量、圆角变量等），供下一步资产生成使用。

### Agent 3：资产生成（Visual Spec → Rendered Assets）

按 `01_platform_formats.md` 中描述的”设计层产出 + 平台适配层产出”两层结构，分别产出：

- 设计层：主视觉稿、色板 token、字体方案、动效脚本（平台无关）
- 平台适配层：分别按搜狗、百度各自的切图规格产出最终 png/apng 资源集

资产生成应包含**自检**：切图尺寸是否匹配规格表、九宫格拉伸区是否落在安全区域（避免拉伸到关键视觉元素上）、动效帧数是否在客户端支持范围内。

### Agent 4：参数装配（Assets → Platform Package）

- 搜狗侧：写 `skin.ini` 全部字段 + 组装 zip → `.ssf`。
- 百度侧：组装标准化工程文件（素材 + 参数 JSON）→ 交给编辑器自动化驱动层 → 产出 `.bps`。

### Agent 5：反馈解析（User Feedback → Targeted Change Instructions）

详见 `04_feedback_loop.md`，这是多轮迭代体验好不好的关键，单独成章。

### Agent 6：QA / 校验

每版产出前的自动校验清单（不是事后可有可无的步骤，是发布前的强制关卡）：

- 文字可读性：候选词文字颜色与背景对比度是否达到可读阈值（自动计算对比度，低于阈值时警告或自动微调并告知用户）
- 关键交互区域是否被装饰性元素遮挡（比如候选词点击区域）
- 两平台版本的视觉一致性检查（自动截图对比色板/构图，标出明显不一致的地方，避免出现”同一版皮肤两个平台看起来像两套设计”的问题）
- 资产规格合规性（尺寸、格式、命名）

QA 失败时不应该把半成品直接推给用户，而应该在 Agent 层内部触发一次自动重试/自动修正，仅在自动修正也失败时才把问题原样暴露给用户（并说明具体是什么问题），这样用户看到的每一版都是”过了自检关”的版本，减少用户浪费反馈轮次在明显能自动发现的问题上。

# 3. 预览引擎设计 —— 核心体验模块

## 3.1 为什么这是整个系统里最不能走捷径的部分

你的原始需求已经把标准定得很清楚：**“预览应该是平常输入法都能干什么，这里的预览就能用那版创造出来的输入法皮肤来进行各种操作来让用户真实体验这个输入法皮肤的效果。”**

这排除了几种”更省事但体验更差”的方案，我要明确列出来，说明为什么不选：

|方案                |为什么不选                                                                                 |
|------------------|--------------------------------------------------------------------------------------|
|生成几张不同状态的静态效果图给用户看|用户看不到真实打字流程（拼音输入、候选词翻页、中英切换、上下滑动手势等），无法判断”这套皮肤在真实使用中好不好用”，只能判断”好不好看”——这偏离了输入法作为工具的本质体验|
|录一段自动演示视频给用户看     |用户仍然是被动观看，无法用自己的打字习惯、自己常用的词去试，无法发现”我常打的这个词候选词露出来不对齐”这类只有真实交互才会暴露的问题                   |
|截图轮播模拟”输入过程”      |假交互，用户一旦想打点别的字就穿帮，体验很快会露馅，且无法承载后续”在预览上直接标注问题”的反馈机制                                    |

**结论：必须自研一个真实的、可交互的虚拟输入法运行时**，运行在 Web 平台里，用当前版本的皮肤资源渲染，响应用户真实的按键/点击输入，跑一个真实的（哪怕简化的）拼音输入引擎，产出真实的候选词序列。这个决定直接影响工作量，但和你确认过的原则一致：**效果优先，不因为工作量大而降级方案**。

## 3.2 预览引擎架构

```
┌───────────────────────────────────────────────────┐
│  Preview Runtime（Web，Canvas/WebGL 或 DOM 混合渲染）│
│                                                     │
│  ┌───────────────┐   ┌────────────────────────┐   │
│  │ 虚拟键盘 UI     │   │ 皮肤渲染层                │   │
│  │ （响应点击/键盘  │──▶│ 读取当前版本的资源清单     │   │
│  │  事件）         │   │ （切图/九宫格/动效帧/色板） │   │
│  └───────────────┘   └────────────────────────┘   │
│           │                                        │
│           ▼                                        │
│  ┌───────────────────────────────────────────┐    │
│  │ 简化拼音输入引擎（真实候选词生成，非假数据）    │    │
│  │ - 拼音串解析 + 分词候选                       │    │
│  │ - 常用词库（可用开源词库，如 rime/opencc 词表） │    │
│  │ - 候选词翻页、联想、中英文切换、符号面板逻辑     │    │
│  └───────────────────────────────────────────┘    │
│           │                                        │
│           ▼                                        │
│  ┌───────────────────────────────────────────┐    │
│  │ 一个"落地文本框"沙盒，用户输入的字实际打出来   │    │
│  │ （模拟真实使用场景：正在某个输入框里打字）      │    │
│  └───────────────────────────────────────────┘    │
└───────────────────────────────────────────────────┘
```

### 关键设计决策：为什么预览引擎需要一个真实（哪怕简化）的拼音引擎，而不是接皮肤图片配假候选词

- 皮肤的候选栏样式（字号、间距、选中态高亮、翻页箭头位置）只有在真实候选词序列（长度不一、多音字、翻页场景）下才能暴露排版问题。假数据大概率是精心挑选的”整整齐齐三个词”，无法测出边界情况（很长的英文候选、生僻字候选、只有一个候选词时的布局等）。
- 用户”像平常用输入法一样”体验，隐含的意思是他们会打自己真实想打的内容，不是照着脚本走 —— 这就要求引擎真的能处理任意拼音输入，而不是识别一个预设列表。
- 这个引擎不需要做到商用输入法级别的智能程度（不需要神经网络级别的联想、不需要个性化学习），但**拼音分词准确度和常用词覆盖率**需要达到”日常输入基本顺畅”的水平，否则用户会把”引擎不够智能”和”皮肤不好看”这两件事搞混，污染反馈信号。方案是采用成熟开源中文词库（如 rime 词库、结巴分词的词频表）做词库底座，不需要从零训练。

### 覆盖的真实输入法操作场景（预览必须能做到，逐项对齐”平常输入法都能干什么”）

- 26 键全键盘拼音输入 + 候选词选择（数字键选词、点击选词、上下翻页）
- 中英文切换
- 符号面板 / 数字面板切换
- 长按/上滑等手势对应的副功能（如有些皮肤会自定义上滑输入符号）
- 候选词区域滚动/翻页动效
- 输入时的按键反馈动效（如果设计里有按下态视觉变化）
- 状态栏图标的各状态展示（中英文状态、输入法开关状态等）
- 横竖屏两种布局（如果目标是同时覆盖 PC 和移动端皮肤，需要分别渲染；PC 端可另外提供”横排候选” vs “竖排候选”切换）

### 平台差异在预览里如何体现

搜狗和百度的候选栏行为、状态栏图标含义、按键功能布局并不完全相同（百度输入法前身特殊，支持自定义按键功能这点在检索资料里被明确提到）。预览引擎需要有**“预览目标平台”切换**（搜狗 / 百度两个 tab 或下拉），分别加载对应平台适配层产出的资源与对应平台的交互逻辑差异，而不是用一套通用逻辑打两个平台的皮子——否则用户在预览里看到的百度效果和真实百度客户端的效果会有出入，这就违背了”真实体验”的初衷。

## 3.3 预览驱动反馈：让”指出问题”直接发生在预览界面里

不只是被动展示，预览界面应该承载反馈采集：

- 用户可以在预览界面里**直接框选/点击某个具体元素**（比如候选词条、某个按键），发起针对该元素的反馈（“这个按键的圆角太大了”），系统自动把这次反馈和 Design Brief 中对应的设计 token/资产 ID 关联起来，减少 Agent 5（反馈解析）靠纯自然语言理解去猜用户具体指的是哪个元素的难度——**这是预览引擎和反馈机制打通带来的体验提升，直接对应你说的”用户可以一轮轮细致地指出意见”**。

## 3.4 技术实现路线

- 渲染层：优先 Canvas（更适合像素级贴图渲染 + 九宫格拉伸计算，性能可控），配合部分 DOM 叠加层处理文字排版与可访问性（文字用 DOM/SVG 渲染比纯 Canvas 绘制文字更清晰、更方便做对比度校验联动）。
- 拼音引擎：可独立于生成管线做成一个可复用的轻量模块（不依赖大模型，纯规则+词典，保证响应速度做到”和真实输入法一样跟手”，不能有明显延迟破坏”真实感”）。
- 资源加载：每个版本的资源清单独立打包（版本化 CDN 路径），支持在版本时间线里秒级切换预览不同历史版本，方便用户对比”这版”和”上一版”的差异，而不需要重新生成。

# 4. 多轮反馈迭代机制

## 4.1 核心诉求回顾

用户”可以根据第一版结果来进行一轮轮细致的指出意见或问题，智能体来调整直到用户觉得这版输入法皮肤没问题”。这意味着系统要支撑的不是”重新生成一遍”，而是**精准的局部修改**，且要让用户感觉到自己上一轮说的话确实被听懂并对应到了具体变化。

## 4.2 反馈输入的两种形式

1. **预览界面内直接标注**（见 `03_preview_engine.md` 3.3）：点选具体元素 + 自然语言描述问题，天然带上下文，定位最准。
1. **自由文字反馈**（不依赖具体元素点选，比如”整体感觉太活泼了，想再稳重一点”）：这类是整体性、氛围性的反馈，需要反馈解析 Agent 做更宽的语义理解，可能需要回到 Design Brief 层面调整而不只是改某个资产参数。

系统需要同时支持这两种，**不能只支持”点选式”反馈然后强迫用户为每个意见都去点选元素**——很多真实反馈是整体性的感受，逼用户拆解成一个个元素点选反而是把负担转嫁给用户，不符合”以用户体验为最终依据”的原则。

## 4.3 反馈解析 Agent 的分类与路由

拿到反馈后先做**问题类型分类**，不同类型路由到管线的不同层级重跑，这是避免”一句话反馈=全部重来”的关键：

|反馈类型          |示例                     |路由到                                                                                                                                 |
|--------------|-----------------------|------------------------------------------------------------------------------------------------------------------------------------|
|具体资产的具体参数问题   |“候选词字体太小”“这个按键颜色太深”    |直接改对应设计 token，只重跑 Agent 3（资产生成）里受影响的那几个资产 + Agent 4（对应平台的打包）                                                                        |
|布局/结构问题       |“候选词应该在上面不是下面”“按键排列太挤了”|回到 Agent 2（视觉设计）调整对应结构参数，重跑受影响的资产生成                                                                                                 |
|整体风格/氛围问题     |“太活泼了，想再稳重点”“想更有中国风一点” |回到 Agent 1（Design Brief）更新风格关键词/情绪基调，触发更大范围的重新生成——但仍尽量保留用户已经认可过的具体细节（比如如果用户之前明确夸过某个图标设计，这类”已获得正向反馈”的元素在大范围调整时应尽量保留或只做适配性微调，而不是无差别推倒）|
|平台特定问题        |“百度这边候选词对不齐，搜狗这边是好的”   |只路由到对应平台的适配层（Agent 3 的平台适配部分 + Agent 4 对应分支），另一平台产出完全不受影响                                                                           |
|功能/交互问题（不是纯视觉）|“候选词翻页太慢”“按下去没反馈”      |路由到预览引擎的交互参数层，这类问题甚至可能不需要重新生成资产，只是调整动效时序参数                                                                                          |

## 4.4 “已获得正向反馈的内容不应被无谓改动”—— 变更范围最小化原则

多轮迭代最容易出的问题是：改了用户提的那一点，结果连带把用户没提意见、其实挺满意的地方也改动了（尤其是走”整体重新生成”路径时）。系统应该维护一份**“已确认满意”标记**（用户对某版某元素明确表达过满意，或者连续两轮反馈都没再提到某个元素，可以从交互记录里推断为”大概率满意”），在重新生成时，对这些元素采用”保留 + 仅做必要的一致性微调”策略，而不是重新随机生成。这对应”效果优先”里一个容易被忽略的维度：**用户对最终结果的满意度，很大程度上取决于系统有没有”记性”，而不是每轮都推倒重来式的”生成质量”本身**。

## 4.5 版本树而非单一版本线

考虑到用户可能会说”这个方向不对，回到第 2 版的感觉，但候选栏用第 4 版的”，版本管理不应该是简单的线性时间线，而应该支持：

- 每个版本可查看、可预览（复用 3.4 的版本化资源加载）
- 支持”以某历史版本为基础分叉出新版本”
- 支持”把某历史版本里的某个元素（比如候选栏设计）合并进当前版本”——这需要资产生成 Agent 的产出在结构上是可拆解、可局部替换的（这也反过来印证了 2.2 节强调的”结构化、可追溯、可单独重跑”设计的必要性——如果没有这个基础，版本树/局部合并根本无法实现）

## 4.6 终止条件

用户明确表达满意（比如点击”确认此版本”）时才进入 `06`（定稿导出）。系统不应该在没有明确信号时自作主张判定”已经改好了”，也不应该在每轮生成后追问”还满意吗”打断体验——保持”生成 → 用户体验 → 用户主动决定是否继续提反馈”的自然节奏，界面上始终清楚地放着”确认使用这版”的入口，但不强迫用户点。

# 5. 前端平台交互设计

## 5.1 页面结构总览

```
┌─────────────────────────────────────────────────────────┐
│  项目创建                                                  │
│  想法输入框 + 参考图上传 + 参考视频上传 + "开始设计"           │
│  （模糊时自动触发提示词优化对话，克制、单轮追问）               │
├─────────────────────────────────────────────────────────┤
│  设计意图确认（Design Brief 卡片）                          │
│  风格关键词 / 色板 / 情绪基调 —— 可编辑，用户可直接调整后再继续  │
├─────────────────────────────────────────────────────────┤
│  工作台（核心界面，占屏幕主体）                                │
│  ┌───────────────┬───────────────────────────────────┐  │
│  │ 左侧：版本时间线  │ 右侧：实时预览（虚拟键盘运行时）        │  │
│  │ + 版本树         │  ┌─────────────────────────────┐  │  │
│  │ + 平台切换 tab   │  │  [搜狗预览] [百度预览]          │  │  │
│  │  （搜狗/百度）    │  │  真实可交互虚拟键盘              │  │  │
│  │                 │  │  点选元素可直接发起反馈           │  │  │
│  │                 │  └─────────────────────────────┘  │  │
│  ├───────────────┴───────────────────────────────────┤  │
│  │ 底部：反馈输入区（文字反馈 + 已标注的元素反馈列表）        │  │
│  └───────────────────────────────────────────────────┘  │
├─────────────────────────────────────────────────────────┤
│  定稿导出                                                  │
│  两平台安装包下载 + 安装引导（尤其百度端如涉及人工确认环节，      │
│  在这里清晰告知进度，不让用户以为卡住了）                       │
└─────────────────────────────────────────────────────────┘
```

## 5.2 关键交互原则

### 预览是主角，不是配角

右侧预览区域应该占据视觉主导地位（不是一个小小的缩略图角落），因为这是用户判断”这版行不行”的核心依据。版本切换、反馈输入都应该设计成不打断预览可见性——比如反馈输入区常驻底部而不是弹窗遮挡预览。

### 生成过程的等待体验

搜狗端生成通常可以很快（纯程序化组装），百度端由于涉及 GUI 自动化驱动，耗时会明显更长且波动更大。前端需要如实反映这种差异，不能用统一的”生成中…“掩盖，而应该分别显示两个平台的生成进度，让用户可以先看搜狗端预览、同时等百度端完成，而不是被迫等最慢的那个平台卡住所有体验。这是”以用户体验为最终依据”在等待状态设计上的具体体现——预览什么时候能看，就什么时候展示，不因为要”统一步调”而人为拖慢已经完成的部分。

### 反馈输入的低门槛

反馈框应该像聊天一样自然（不需要用户学习”如何正确提反馈”的规则），点选元素只是加分项、不是必需项。这样”细致地一轮轮指出问题”这件事对用户来说门槛足够低。

### 移动端/桌面端预览的呈现

由于百度、搜狗皮肤在 PC 端和移动端外观、交互都有差异（检索资料证实两端是不同格式体系），如果项目范围包含移动端皮肤，前端需要有清晰的”预览设备”切换（PC 虚拟键盘 vs 手机虚拟键盘），并且默认聚焦当前确认的目标场景，避免用户混淆”我现在看到的到底是哪端的效果”。

*(注：当前架构文档聚焦 PC 端两大平台，如需同时支持移动端 App 内置皮肤，需要在此基础上新增移动端预览运行时模块，原则相同，不再展开。)*

### 版本对比而非纯线性历史

参考 `04_feedback_loop.md` 5 节的版本树设计，前端应该提供”并排对比两个版本”的能力（左右分屏预览两个不同版本），这比纯粹的”版本列表点开单看”更符合用户实际决策方式（人在比较中做判断，不是在孤立展示中做判断）。

## 5.3 提示词优化对话的分寸

模糊想法触发的优化对话，应遵循：

- 优先从已有素材（参考图/视频）推断，能推断的不问。
- 真正需要问的，一次只问一个最关键的缺口（例如”这套皮肤主要是你自己日常用，还是想做成分享给别人用的更有记忆点的风格？“这类能显著收窄方向的问题），不做问卷式连续追问。
- 用户随时可以说”你看着办”跳过优化对话，直接进入生成，此时智能体基于已有信息给出合理默认判断并在 Design Brief 里注明”以下为智能体推断，非用户明确指定”，方便用户在确认环节一眼看出哪些是需要重点检查的推断内容。

# 6. 风险登记与需要提前做的技术验证

这一章的目的是把方案中”尚未证实、需要拿真实环境测试才能确认”的部分明确列出来，不混在”已确定可行”的部分里，避免团队基于乐观假设去做后续排期。

## 6.1 高优先级：百度编辑器自动化可行性 Spike

**风险**：整个百度出口（.bps 真实安装包）的可行性系于此。

**需要验证的具体问题**：

1. BDPYSkinEditor 官方正式下载渠道是什么（需要找百度官方页面直接下载，而非论坛/网盘镜像，涉及来源可信度和是否有官方授权批量使用的问题，可能需要与百度方面沟通商务合作，检索资料中提到过”合作联系”邮箱）。
1. 编辑器是否需要登录/联网校验才能新建工程、导入素材、导出文件——如果导出这一步强制要求联网校验且有频率限制，无人值守批量生成会受限。
1. 编辑器的 UI 控件是否有可访问性标识（Windows UI Automation 树上能否稳定识别到每个按钮/输入框），还是纯自绘界面导致只能用像素坐标定位（后者会显著提高自动化脚本的脆弱性和维护成本）。
1. 编辑器是否支持导入”工程文件”（比如之前保存的 .bps 或中间工程格式）实现”预填参数后一键导出”，还是每次都必须从新建工程走完整个人工流程（后者意味着自动化脚本要模拟完整的多步骤操作序列，环节越多，出错概率越高）。
1. “检错”功能返回的结果是否有程序可读的形式（比如状态栏文字/弹窗文字），能否被自动化脚本读取用于判断是否需要重试。

**建议的验证方式**：搭建一个独立的 Windows 沙箱环境，安装编辑器，人工先走一遍完整流程记录每一步的界面结构，再用自动化工具（pywinauto 等）逐步替换人工点击，记录哪些步骤能稳定自动化、哪些不能，产出一份”自动化可行性评估报告”，再决定是否需要 4.6 节提到的人工监督兜底方案，以及兜底方案在多大比例的情况下会被触发。

## 6.2 中优先级：搜狗 skin.ini 完整字段核实

虽然搜狗路径整体可行性高，但 `skin.ini` 的**完整**字段列表（尤其是不常用但影响体验的字段，比如 apng 帧率控制、拉伸区精确语法）需要用真实样本核实，不能只靠搜索摘要里的碎片信息。建议：下载数十个真实上架的搜狗皮肤样本，批量改名解压，做字段频率统计和语法归纳，作为参数装配 Agent 的权威参数字典来源，比单纯读官方教程 PDF 更全面（教程可能只覆盖基础用法，真实皮肤作者摸索出的进阶用法很可能没写进官方文档）。

## 6.3 中优先级：预览引擎的拼音引擎选型

需要评估候选开源词库/分词方案在”响应速度”和”日常词汇覆盖率”之间的平衡，实际选型需要用真实测试语料跑一遍，确认不会出现明显的”常用词打不出来”的尴尬情况破坏预览可信度。

## 6.4 低优先级但需要关注：版本兼容性长期维护

搜狗侧确认存在版本兼容标记机制（min/max 版本号），百度侧虽未直接证实但大概率存在类似机制。这意味着**两个平台的客户端升级都可能让历史生成的皮肤失效或显示异常**，系统需要有长期的”监测 + 回归测试”机制，而不是一次性生成完就不管——这不是初期架构必须解决的问题，但需要在路线图里占一个位置，避免上线后被动。

## 6.5 风险优先级排序与建议顺序

1. **先做 6.1（百度自动化 Spike）**——这是唯一可能导致方案根本性调整（回退到降级路径甚至重新讨论产品范围）的风险，越早验证越好。
1. 6.1 验证的同时可以并行推进搜狗全链路（6.2）和预览引擎（6.3），这两块几乎不依赖 6.1 的结论，可以独立往前走，不必等百度那边出结果才开工。
1. 6.4 纳入长期运营计划，不阻塞首个版本上线。
