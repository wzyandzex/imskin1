## 0. 设计前提与硬性原则

本系统有两条**约束级**原则。它们不是"时间允许再做"的加分项，而是评审任何设计、代码、方案时的一票否决线。

### 原则一：效果优先于工作量

任何环节，只要更深入的设计、更多的代码能让**最终生成的皮肤质量**或**用户的真实体验**更好，就不能因为想省工作量而退到最小方案。

这条原则直接否决以下几类捷径（本文档会在相关章节反复引用这张否决表）：

| 被否决的最小方案 | 否决理由 |
|---|---|
| 生成一张静态效果图当作"皮肤" | 用户拿不到能装进输入法真实使用的产物 |
| 预览用截图轮播 / 录屏演示 | 用户无法用自己的输入习惯真实体验，穿帮即失真 |
| 逆向猜一个"假的 .bps 生成器" | 客户端可能做签名/哈希校验，格式随编辑器升级漂移，无官方对齐渠道，长期必碎 |
| 一个大模型端到端吐最终文件 | 无法定位局部问题、无法单独重跑、每轮推倒重来 |
| 预览接皮肤图 + 一组写死的假候选词 | 测不出真实拼音输入下的排版边界（超长候选、生僻字、单候选、翻页） |

> **重要澄清**：搜狗直接编程生成、百度自动化驱动官方编辑器，这两条路径看起来"更重"，但它们恰恰是**效果优先与工程稳健一致**的选择——不是走捷径，而是这条路本来就是长期最优解。效果优先 ≠ 无脑堆量，而是**为"长期稳定产出正确产物"投入**，拒绝"短期能跑、随时会碎"。

### 原则二：前端设计以用户真实体验为最终依据

前端所有取舍以"用户注重什么、怎样体验感更好"为准，而非实现是否简便。核心推论：

- **预览必须是"像日常使用输入法一样"的真实交互运行时**，不是设计稿展示。
- **等待状态如实分平台呈现**：搜狗端先好就先让用户体验，绝不为"统一步调"人为拖慢已完成的部分。
- **反馈门槛要低到聊天级别**：点选元素是加分项，不是必须动作；整体性感受（"太活泼了"）必须被一等支持。

### 技术路线定位（Plan A）

本期覆盖**两大厂商 × 两种设备 = 四个出口**：搜狗 PC、搜狗移动、百度 PC、百度移动。基于第一轮平台调研（见 [§2 平台格式规格](#2-平台格式规格与生成策略)）：

- **搜狗 PC 皮肤（`.ssf`）**：格式公开、可编程直接生成，端到端全自动，零人工干预。
- **百度 PC 皮肤（`.bps`）**：无公开写规范，走"标准化工程文件 + 自动化驱动官方皮肤编辑器导出"路径；其中"GUI 自动化的可行性与稳定性"是**高优先级技术假设**，已作为显式风险管理（[§11.1](#111-p0百度编辑器自动化可行性)），不藏在乐观假设里。
- **搜狗移动 / 百度移动皮肤**：移动端皮肤是本期硬需求，其外观、交互（九宫格 T9、手势、按键音效/振动、滑行输入等）与 PC 端有本质差异，需**独立的移动端预览运行时与适配管线**。移动端各自的皮肤文件格式、是否可编程直生、是否需驱动官方 DIY 工具，**尚未完成第一轮调研**，因此**与百度 PC 自动化并列为 M0 阶段必须优先验证的关键假设**（[§11.5](#115-p0移动端皮肤格式与生成路径第一轮调研)），同样不藏在乐观假设里。

> **移动端路径选择原则（先于事实即可确立）**：与 §2.1/§2.2 完全一致——**格式公开可写则编程直生（首选）；无公开规范则驱动官方工具并做人工兜底；绝不逆向猜一个"假格式生成器"**。调研只决定每个移动端出口落在这条原则的哪一档，不改变原则本身。

## 1. 系统总览

### 1.1 一句话定位

> 用户用一段模糊的想法（可带参考图/视频），系统自动产出可直接安装到**搜狗、百度两大输入法的 PC 端与移动端（共四个出口）** 的皮肤安装包；用户在网页里像**真的打字一样**体验这版皮肤（PC 虚拟键盘 / 手机虚拟键盘可切换），再用自然语言一轮轮提意见，系统做**精准局部**调整直到用户满意后定稿导出。

### 1.2 端到端用户旅程

```
① 输入采集
   ├─ 一段模糊/清晰的文字想法
   ├─ （可选）参考图 / 参考视频
   └─ （模糊时）克制的提示词优化对话，把想法收敛成可执行需求
        ↓
② 设计意图生成（Design Brief）
   智能体把"想法 + 参考素材"转成结构化设计简报：
   风格关键词 / 配色 / 材质纹理 / 布局取舍 / 动效意向 / 目标情绪
   —— 展示给用户【确认或编辑】后才继续
        ↓
③ 视觉设计（Visual Spec）
   高保真设计稿 + 结构化设计 token（颜色/间距/圆角/字重变量）
        ↓
④ 视觉资产生成
   设计层产出（平台无关）+ 平台适配层产出（按各出口切图规格）
   —— 平台适配层 = 厂商 × 设备 四象限：搜狗PC / 搜狗移动 / 百度PC / 百度移动
        ↓
⑤ 四出口打包
   ├─ 搜狗PC：编程组装 skin.ini + 切图 → .ssf（全自动）
   ├─ 百度PC：标准化工程 → 驱动官方编辑器 → .bps（自动化 + 人工兜底队列）
   └─ 搜狗移动 / 百度移动：按 M0 调研结论落到"编程直生"或"驱动官方DIY工具"（策略同上）
        ↓
⑥ 实时预览（核心体验）
   用户在平台内直接"打字体验"这版皮肤（自研虚拟输入法运行时）
   —— 设备维度：PC 虚拟键盘 / 手机虚拟键盘（含九宫格、手势、按键音效/振动、滑行输入）
   —— 厂商维度：搜狗 / 百度，各自还原真实交互差异
        ↓
⑦ 多轮反馈迭代
   自然语言 / 在预览上点选元素 → 反馈解析 → 定位到具体参数或资产 → 精准重跑
        ↓
⑧ 定稿导出
   用户明确"确认此版本" → 导出四出口正式安装包 + 安装引导
```

**关键流程性约束**：②→③ 之间有一道**强制的用户确认关卡**。省掉它 short-term 省事，long-term 是重大减分——辛苦生成一版才发现方向就错了，成本远高于多点一次确认。

### 1.4 架构风格与关键决策一览（ADR 摘要）

| # | 决策 | 选择 | 一句话理由 | 详见 |
|---|---|---|---|---|
| ADR-1 | 生成方式 | **多 Agent 结构化管线**，非端到端黑盒 | 局部反馈要能局部重跑 | §3.1 |
| ADR-2 | 搜狗出口 | **绕开 GUI，直接编程生成 .ssf** | 格式公开，直生比自动化 GUI 更稳更快 | §2.1 |

## 2. 平台格式规格与生成策略

### 2.1 搜狗 PC 皮肤（`.ssf`）— 全自动生成路径

**已确认事实**

- 容器：标准 zip，重命名 `.ssf` 即为完整皮肤；反之改名 `.zip` 可解压查看/修改。
- 内容：一个 `skin.ini` + 若干 `.png`/`.apng`。
- 安装：双击后拷贝到安装目录 `allskin`，解压到 `skin`，随后出现在皮肤列表。
- 官方提供"设计-切图-生成"标准流程与皮肤编辑器 ⇒ 存在明确的切图规格表（候选栏、拼音区、云候选区、键盘大背景、9键/26键、弹泡等）。

**生成策略：编程直接组装，绕开官方 GUI（ADR-2）**

1. 按官方切图规格生成/切割各分辨率资源图（背景、按键前景/背景、状态栏、候选栏、弹泡动画等）。
2. 程序化写出 `skin.ini`，覆盖全部可控节区（**须在验证阶段用真实皮肤样本逐项核实**，当前已知需覆盖）：
   - 输入窗口背景与九宫格拉伸区（横排/竖排两套）
   - 候选词区域：字体、字号、颜色（选中态/非选中态/序号态）
   - 拼音串显示区域位置与样式
   - 状态栏图标集（中英切换、全半角、软键盘等各状态）
   - 按键背景与前景（若支持虚拟键盘皮肤）
   - apng 动效帧序列与帧率
   - 版本兼容标记（若存在 min/max 版本字段，写入以避免新旧客户端渲染错位）
3. 按目录结构打包 zip，重命名 `.ssf`。

**为什么不用官方编辑器**：编辑器是给人手动操作的 GUI，无已知命令行接口。格式既然透明可写，直接生成比自动化一个会随界面变化而失效的 GUI 更可靠、更快。这是效果优先与工程稳健一致的情形。

### 2.2 百度 PC 皮肤（`.bps`）— 可编程直生路径（已落地）

> **2026-08 更新**：经 open-reverselab 逆向笔记（真实皮肤 `纯白/标题/四叶` 解包 + 安装器 `skininst.exe` 逆向）确证，百度 PC 皮肤 = **无注释、纯 deflate 的标准 ZIP**，内部是 `skin.ini`(UTF-16LE) + `Skin.xml`(UTF-8) + `Candidate.ini/xml` + `Status.ini/xml` + 若干 png/gif。无加密、无私有头、无魔数校验（除 zip 本身）。`skininst.exe` 仅做 zlib 解压、无自定义解密。**因此推翻此前的"驱动官方编辑器"方案（ADR-3），改为可编程直生（ADR-2 同源）**，由 `baidu-pc-adapter` 落地。

**已确认事实**

- 容器：标准 ZIP（deflate），改后缀 `.bps` 分发；`Content-Disposition: attachment; filename=<皮肤名>.bps`。
- 内容：`skin.ini`(UTF-16LE) + `Skin.xml` + `Candidate.xml`(候选窗) + `Status.xml`(状态条) + 位图。
- 元数据 `[Skin]`：`uversion/email/name/discrip/time(17位)/guid/account/author/iniver/version`。
- 布局 `Candidate.xml`/`Status.xml`：`<UI><CCandidateWin>/<CStatusWin>` + `CBDButton/CBDImage`（`normalImg/overImg/downImg` + `stretchArea` 九宫格 + `drawStyle` 0/1/2）。
- 安装：`skininst.exe -silent -notify-error "<badge>"` 解包到 `%LocalAppData%\Low\Baidu\BaiduPinyin\Skin\<Guid>\` 并登记 `SkinList.ini`。

**生成策略：编程直接组装（ADR-2）**

1. `baidu-pc-adapter/skin-ini.ts` 写 `[Skin]` 元数据（UTF-16LE）。
2. `skin-xml.ts` 写 `Skin.xml`（UTF-8，与 ini 等价，兼容旧/新加载器）。
3. `ui-xml.ts` 写 `Candidate.xml` + `Status.xml`（CBDButton/CBDImage + 九宫格 stretchArea）。
4. `bps.ts` 打 store-zip → `.bps`（浏览器安全；真机若强制 deflate 仅改打包层）。

**仍待真机核实**：手写 zip 是否被当前主流百度输入法接受安装（逆向证据强烈支持，未在本环境真机验证）。

**iOS 边界**：百度 iOS 输入法为系统扩展(App Extension)，沙盒内运行，无外部皮肤包导入通道；皮肤仅走服务端下发 + App 内 AI 皮肤（上传图片 AI 生成）。DIY 生成器**无法产出可导入的 iOS 皮肤包**，仅能产设计稿供用户走 AI 皮肤。故四出口 = 搜狗PC / 搜狗Android / 百度PC / 百度Android。

### 2.3 四出口资产复用（ADR-6）

容器和配置层各不相同，但**视觉设计阶段（配色/构图/风格/动效意向）在四个出口间共享**——同一版皮肤在四个出口应是"同一个设计"，只是各自精确切图与适配控件坐标系、交互能力。

资产产出分两层：

1. **设计层产出（平台无关）**：主视觉稿、色板 token、字体方案、动效脚本、（移动端还含）按键音效方案与触感/振动意向 —— 一份。
2. **平台适配层产出（厂商 × 设备 四象限，各自独立）**：搜狗PC / 搜狗移动 / 百度PC / 百度移动 四套切图与配置，分别生成，允许象限特定细节调整：
   - PC 与移动的**切图规格、键盘布局（PC 26键为主 vs 移动 九宫格+全键盘）、坐标系**完全不同，各自计算。
   - 移动象限额外产出 PC 象限没有的资产：**九宫格布局切图、按键音效文件、按下/弹跳动效帧、手势反馈资产**（具体以 M0 调研的各平台可自定义能力为准）。

**收益（精准定位、不做无谓整体重跑）**：

- "整体配色再冷一点" → 四象限同步重走适配。
- "搜狗PC候选词太小"（象限特定）→ 只重跑搜狗PC适配管线，其余三象限已生成版本完全不动。
- "手机上按键音太闷"（设备特定）→ 只重跑移动象限的音效资产，PC 象限完全不受影响。

重跑越少，等待越短，越不会在没问题的地方引入新问题。

> **2026-08 更新**：经 open-reverselab 逆向笔记（真实 APK `com.baidu.input` v13.3.6.113 jadx 反编译）确证，手机端 `.bds` = 外层标准 ZIP（与 PC 相同），内部文件结构完全不同：`Info.txt`(UTF-8) + `Token.txt`(MD5) + `preview.png` + `port/`(竖) + `land/`(横) 布局 `.ini`/`.cnd`/`.pop` + `css.ini` 样式 + 可选 `keyshape.json`+`keyshape_*.png`、`diy/config.json`、`bar.png`/`icon.png`/`demo.png`。由 `baidu-mobile-adapter` 落地。

## 3. 智能体编排管线

### 3.1 设计原则（ADR-1）

每个 Agent 的输出必须**结构化、可追溯、可单独重跑**，而非一个大模型端到端吐最终文件：

- 用户反馈往往是局部的（"候选词字太小"）。黑盒端到端无法定位、无法局部重跑，只能整体重来——既慢又容易改坏用户已满意的部分。
- 每层中间产物（Design Brief / Visual Spec / 资产清单）都应允许用户在 UI 上查看甚至编辑，比"猜用户想要什么"可靠。

**这条原则是版本树、局部合并、精准重跑三大能力的共同地基**（见 §5.5）。地基不牢，上层皆空谈。

### 3.2 Agent 契约总表

> 原文强调"可单独重跑"却没给契约。契约是"可单独重跑"能否成立的地基，此处补齐。每个 Agent 是**纯函数式**的：给定相同输入 + 相同随机种子 ⇒ 可复现产出；产出带 `provenance`（溯源）字段记录输入哈希与依赖版本，供缓存命中与增量重跑判断。

| Agent | 输入 | 输出 | 可单独重跑触发 |
|---|---|---|---|
| A1 意图理解 | 文字想法 + 参考图/视频（可选）+ 追问回答 | `DesignBrief` | 整体风格/氛围类反馈 |
| A2 视觉设计 | `DesignBrief` | `VisualSpec` + 设计 token + 高保真设计稿 | 布局/结构类反馈 |
| A3 资产生成 | `VisualSpec` + 目标平台集 | `AssetBundle`（设计层 + 平台适配层） | 具体资产参数类反馈 |
| A4 参数装配 | `AssetBundle` + 目标平台 | 搜狗 `.ssf` / 百度工程 → `.bps` | 打包参数变更 |
| A5 反馈解析 | 用户反馈（文字 / 元素点选）+ 当前版本上下文 | `ChangeInstruction`（分类 + 路由 + 目标节点 ID） | 每轮反馈 |
| A6 QA/校验 | 任一版待发布产物 | `QAReport`（通过/警告/失败 + 定位）| 每版产出前 |

### 3.3 各 Agent 详解

**A1 意图理解（Idea → Design Brief）**

- 判定信息量：缺少"风格 / 配色 / 情绪基调"三者中任意两项以上明确指向时，触发**提示词优化对话**。遵循"一次最多问一个关键问题"的克制原则，优先根据已给参考素材推断合理默认值，不做问卷式连续追问。
- 参考图：跑视觉特征提取（主色调、构图密度、材质倾向如玻璃拟态/扁平/拟物、圆角程度、字重倾向）。
- 参考视频：抽关键帧（场景/色彩变化点）同样提取；若含动效意向（如"输入时有粒子效果"），识别为**行为性需求**并路由给动效设计，而非静态资产设计。
- 输出 `DesignBrief`（结构见 §7.2），**必须展示给用户确认/编辑**后才继续。用户可说"你看着办"跳过，此时 Brief 中标注哪些是智能体推断（非用户明确指定），方便确认环节重点检查。

**A2 视觉设计（Design Brief → Visual Spec）**

把简报转成可执行视觉规格：每个 UI 元素（候选栏/按键/状态栏/拼音条）长什么样、配色层级、圆角/阴影/描边参数、字体族与字重、动效具体时序曲线。产出**高保真设计稿**（生成真实切图前先让用户看到大致方向）+ 结构化**设计 token**（颜色/间距/圆角变量）。

**A3 资产生成（Visual Spec → Rendered Assets）**

按 §2.3 两层结构产出。资产生成含**自检**：切图尺寸是否匹配规格表、九宫格拉伸区是否落在安全区（避免拉伸到关键视觉元素）、动效帧数是否在客户端支持范围。

**A4 参数装配（Assets → Platform Package）**

- 搜狗侧：写全 `skin.ini` 字段 + 组装 zip → `.ssf`。
- 百度侧：组装标准化工程（素材 + 参数 JSON）→ 交编辑器自动化驱动层 → 产出 `.bps`。

**A5 反馈解析**：见 §5，多轮迭代体验的关键，单独成章。

**A6 QA/校验**：每版产出前的**强制关卡**（非事后可选步骤），清单见 §3.4。

### 3.4 QA 校验清单（发布前强制关卡）

- **文字可读性**：候选词颜色与背景对比度是否达可读阈值（自动计算对比度，低于阈值时警告或自动微调并告知用户）。
- **交互区遮挡**：关键交互区域（如候选词点击区）是否被装饰性元素遮挡。
- **四出口视觉一致性**：自动截图对比色板/构图，标出明显不一致处，避免"同一版皮肤在四个出口像几套设计"。
- **资产规格合规**：尺寸、格式、命名。

**失败处理**：QA 失败不把半成品推给用户，先在 Agent 层内部触发一次自动重试/自动修正；仅当自动修正也失败，才把问题原样暴露（并说明具体是什么）。用户看到的每一版都是"过了自检关"的版本，避免用户浪费反馈轮次在能自动发现的问题上。

## 4. 预览引擎设计 — 核心体验模块

### 4.1 为什么这是最不能走捷径的部分

原始需求已把标准定死：**"预览应该是平常输入法都能干什么，这里的预览就能用那版创造出来的皮肤来进行各种操作，让用户真实体验这套皮肤的效果。"** 这排除了 §0 否决表里"静态图/录屏/截图轮播"三种更省事但体验更差的方案。

**结论：必须自研一个真实的、可交互的虚拟输入法运行时**，运行在 Web 里，用当前版本皮肤资源渲染，响应用户真实按键/点击，跑一个真实（哪怕简化）的拼音引擎，产出真实候选词序列。这个决定显著增加工作量，但与效果优先原则一致。

### 4.2 预览引擎架构

```
┌────────────────────────────────────────────────────────┐
│  Preview Runtime（Web，Canvas/WebGL + DOM 混合渲染）    │
│                                                          │
│  ┌───────────────┐    ┌────────────────────────────┐   │
│  │ 虚拟键盘 UI     │    │ 皮肤渲染层                   │   │
│  │ 响应点击/键盘   │──▶ │ 读取当前版本资源清单          │   │
│  │ 事件           │    │ （切图/九宫格/动效帧/色板）    │   │
│  └───────────────┘    └────────────────────────────┘   │
│         │                                                │
│         ▼                                                │
│  ┌──────────────────────────────────────────────┐      │
│  │ 简化拼音输入引擎（真实候选词生成，非假数据）      │      │
│  │ - 拼音串解析 + 分词候选                          │      │
│  │ - 拼音内核 + 词库（librime/libpinyin 系 + 词频表）│      │
│  │ - 候选翻页、联想、中英切换、符号面板逻辑           │      │
│  └──────────────────────────────────────────────┘      │
│         │                                                │
│         ▼                                                │
│  ┌──────────────────────────────────────────────┐      │
│  │ "落地文本框"沙盒：用户输入的字实际打出来          │      │
│  │ （模拟真实场景：正在某个输入框里打字）            │      │
│  └──────────────────────────────────────────────┘      │
└────────────────────────────────────────────────────────┘
```

### 4.3 为什么预览引擎需要真实（哪怕简化）的拼音引擎，而非配假候选词

- 候选栏样式（字号/间距/选中态高亮/翻页箭头位置）只有在**真实候选词序列**（长度不一、多音字、翻页场景）下才暴露排版问题。假数据往往是精心挑的"整整齐齐三个词"，测不出边界（超长英文候选、生僻字、单候选布局）。
- "像平常用输入法一样"隐含用户会打自己真实想打的内容 ⇒ 引擎必须能处理任意拼音，而非识别预设列表。
- 引擎无需商用级智能（不需神经网络联想/个性化学习），但**拼音分词准确度和常用词覆盖率**要达到"日常输入基本顺畅"，否则用户会把"引擎不够智能"和"皮肤不好看"搞混，污染反馈信号。方案：用成熟开源拼音**内核**（如 librime / libpinyin 系）+ 开源词库/词频表做底座，不从零训练。

> **选型澄清（避免常见误用）**：拼音输入引擎做的是"拼音串 → 汉字候选"；**结巴(jieba)是中文分词（汉字串 → 词），不是拼音输入引擎，不能拿来当 IME 内核**，只适合用来构建/清洗词库、统计词频。`pypinyin` 做"汉字 → 拼音"（反方向），可用于离线构建九宫格 T9 词典。具体开源方案的仓库地址与维护状态需在选型 Spike 中核验（§11.3/§11.6）。

### 4.4 必须覆盖的真实输入法操作场景

逐项对齐"平常输入法都能干什么"：

- 26 键全键盘拼音输入 + 候选词选择（数字键选词、点击选词、上下翻页）
- 中英文切换
- 符号面板 / 数字面板切换
- 长按 / 上滑等手势对应副功能（如某些皮肤自定义上滑输入符号）
- 候选词区域滚动 / 翻页动效
- 输入时按键反馈动效（若设计含按下态视觉变化）
- 状态栏图标各状态展示（中英文状态、输入法开关状态等）
- 横竖排候选切换（PC 端）

> 本节为 PC 端场景清单；移动端（九宫格 T9、竖屏、手势、按键音效/振动、按下动效等）的完整场景见 §4.8。

### 4.5 平台差异在预览里如何体现

搜狗和百度的候选栏行为、状态栏图标含义、按键功能布局并不完全相同（百度支持自定义按键功能）。预览引擎需有**"预览目标平台"切换**（搜狗/百度 tab），分别加载对应平台适配层资源与交互逻辑差异，而非用一套通用逻辑打两个平台——否则预览里的百度效果和真实百度客户端有出入，违背"真实体验"初衷。

### 4.6 预览驱动反馈：让"指出问题"直接发生在预览里

预览不只被动展示，还承载反馈采集：用户可在预览界面**直接框选/点击某个具体元素**（候选词条、某个按键）发起针对该元素的反馈（"这个按键圆角太大"），系统自动把这次反馈与 Design Brief 中对应的设计 token / 资产 ID 关联，降低 A5 靠纯自然语言猜"用户指哪个元素"的难度。这是预览与反馈打通带来的体验提升。

### 4.7 技术实现路线

- **渲染层**：优先 Canvas（适合像素级贴图 + 九宫格拉伸计算，性能可控），配合部分 DOM 叠加层处理文字排版与可访问性（文字用 DOM/SVG 比纯 Canvas 更清晰，也方便与对比度校验联动）。
- **拼音引擎**：独立于生成管线的可复用轻量模块（纯规则 + 词典，不依赖大模型），保证响应"和真实输入法一样跟手"，无明显延迟破坏真实感。
- **资源加载**：每版资源清单独立打包（版本化 CDN 路径），版本时间线里秒级切换预览不同历史版本，方便对比"这版 vs 上一版"，无需重新生成。

### 4.8 移动端虚拟输入法运行时（ADR-8）

移动端是本期硬需求，且**手机输入法的真实使用体验与 PC 差异极大**——用户在手机上大量依赖九宫格、手势、按键音效与触感、按下动效、滑行输入。若预览沿用 PC 那套一维键盘逻辑，用户看到的和真机严重不符，直接违背"真实体验"初衷（原则二）。因此移动端需**独立的虚拟输入法运行时**，与 PC 运行时共享皮肤渲染与版本加载基座，但交互层完全重写。

**必须真实还原的移动端场景（预览逐项覆盖，对齐"手机上平常输入法都能干什么"）**：

- **九宫格(9键 T9)拼音输入**：一个按键对应多个字母（如 2=abc），需真实的 T9 拼音候选生成逻辑，不是把 26 键结果套壳。九宫格是移动中文输入的主力方式，不能只做全键盘。
- **26 键全键盘 + 九宫格 一键切换**，两套布局分别用当前皮肤资源渲染。
- **竖屏为主布局**：手机键盘框（机型外壳 mockup + 键盘区 + 落地文本框），让用户看到皮肤"装在手机上"的样子。
- **按键长按弹出**（长按上排数字/长按候选切换等）。
- **上滑输入符号/数字**（很多皮肤自定义上滑副功能）。
- **滑行输入（swipe / glide typing）**（若目标平台支持）。
- **候选词横向滑动翻页**。
- **按键音效**：用 Web Audio 播放按键音，还原皮肤自带音效方案（移动皮肤音效是重要卖点，不能省）。
- **按键触感/振动**：用 `navigator.vibrate` 尽力还原（浏览器支持有局限，需在预览中明示"真机振动更强"，不假装完全等价）。
- **按下/弹跳动效**：按键按下时的放大/弹跳/波纹动效，逐帧还原设计。
- **符号 / 表情 / 数字面板切换**。
- **多机型 DPI 预览**：提供典型屏幕密度档位切换，让用户看到皮肤在不同机型上的清晰度与布局，暴露"高密度屏发虚"这类只有分设备预览才发现的问题。

**分厂商差异**：搜狗移动与百度移动在键盘布局、功能栏、候选栏、可自定义能力（百度移动可能支持自定义按键功能等超视觉能力）上不同，移动运行时同样按厂商加载各自交互逻辑与资源，不用一套通用逻辑打两家（同 §4.5）。

**技术要点**：

- **分层渲染**（还原度与可维护性兼顾）：① 背景层（静态图 / 透明视频 / Lottie 动态背景）→ ② 按键层（DOM，便于换肤/文字/单键样式/命中检测/可访问性）→ ③ 特效层（Canvas/WebGL 覆盖，`pointer-events:none`，画粒子/闪电/水波/滑行拖尾等重特效）→ ④ 候选/工具栏层（DOM）。DOM 管交互与文字，Canvas 管炫效。
- **触摸/手势**：统一用 Pointer Events（覆盖触摸 + 鼠标，桌面也能演示），容器 `touch-action:none`；长按用定时器、上滑看 Y 位移、滑行采样轨迹点转成经过键序列喂引擎并交 Canvas 画拖尾。
- **按键音**：Web Audio（AudioContext + 预解码 AudioBuffer），低延迟、可叠加；**注意浏览器自动播放策略——AudioContext 必须在首次用户手势里 `resume()`**，否则无声。
- **振动**：`navigator.vibrate` 仅部分 Android 浏览器支持，**iOS Safari 完全不支持**；预览在不支持环境降级为视觉/音效提示并**明示"真机上为振动"**，不假装等价。
- **按下动效**优先 CSS `transform/opacity`（GPU 合成、跟手、易还原弹性曲线）；重特效才上 Canvas/WebGL。
- **九宫格 T9 引擎**：作为拼音引擎的一个输入模式扩展——引擎内核选型**只需看 26 键能力**，9 键靠前置一层"数字键→字母集合展开 + 拼音音节切分（合法音节 Trie/DAG 上做 DP 剪枝）+ 词频/语言模型排序"适配层复用同一词典（见 §4.3、§11.6）。
- **多机型 DPI 预览**：用机型预设（逻辑尺寸 dp + DPR + 安全区 `env(safe-area-inset-*)`）在缩放容器/iframe 内按逻辑分辨率渲染，并按 DPR 切换 @2x/@3x 位图，直观暴露"高密度屏发虚"。
- **分平台外观基线**：iOS（独立圆角键帽 + 字符预览气泡 + 地球键 + QuickType 候选条）与 Android（更扁平、可无键边框、允许振动）各出一套外观基线；同一皮肤两平台呈现不同。

移动运行时同样要求按键→候选延迟 ≤ 50ms 的跟手感。

> **待真机审计项**：搜狗移动与百度移动**当前版本**的功能栏图标顺序、候选栏高度与翻页交互、皮肤/特效体系等**像素级差异**，须用真机或官方素材做一次视觉审计后再固化到预览分档，不基于通用描述臆造（并入 §11.5 移动端调研）。

## 5. 多轮反馈迭代机制

### 5.1 核心诉求

用户"可以根据第一版结果一轮轮细致指出意见，智能体调整直到用户觉得这版没问题"。系统要支撑的不是"重新生成一遍"，而是**精准的局部修改**，且让用户感到自己上一轮说的话确实被听懂并对应到具体变化。

### 5.2 反馈的两种形式（都要一等支持）

1. **预览内直接标注**（§4.6）：点选元素 + 自然语言，天然带上下文，定位最准。
2. **自由文字反馈**（不依赖点选，如"整体太活泼，想稳重点"）：整体性、氛围性反馈，需更宽的语义理解，可能回到 Design Brief 层调整。

**不能只支持点选式反馈**然后强迫用户为每个意见都去点选——很多真实反馈是整体感受，逼用户拆解成元素点选是把负担转嫁给用户，违背原则二。

### 5.3 反馈解析与路由（避免"一句话反馈=全部重来"的关键）

先做**问题类型分类**，不同类型路由到管线不同层级重跑：

| 反馈类型 | 示例 | 路由到 |
|---|---|---|
| 具体资产参数 | "候选词字太小""这按键颜色太深" | 改对应设计 token，只重跑 A3 受影响资产 + A4 对应平台打包 |
| 布局/结构 | "候选词应在上面""按键排列太挤" | 回 A2 调结构参数，重跑受影响资产 |
| 整体风格/氛围 | "太活泼，想稳重点""更有中国风" | 回 A1 更新风格关键词/情绪，触发更大范围重生成，**但保留已获正向反馈的元素** |
| 平台特定 | "百度候选词对不齐，搜狗是好的" | 只路由对应平台适配层（A3 平台适配部分 + A4 对应分支），另一平台不受影响 |
| 功能/交互（非纯视觉） | "候选翻页太慢""按下去没反馈" | 路由到预览引擎交互参数层，可能不需重新生成资产，只调动效时序参数 |

### 5.4 变更范围最小化：已获正向反馈的内容不应被无谓改动

多轮迭代最容易出的问题：改了用户提的那点，连带把用户没提意见、其实挺满意的地方也改了（尤其走整体重生成路径时）。系统维护一份**"已确认满意"标记**（用户明确表达过满意，或连续两轮反馈都未再提及某元素 ⇒ 从交互记录推断大概率满意），重新生成时对这些元素采用"保留 + 仅做必要一致性微调"策略，而非重新随机生成。

> 这对应效果优先里一个易被忽略的维度：**用户对最终结果的满意度，很大程度取决于系统有没有"记性"，而非每轮推倒重来式的生成质量本身。**

### 5.5 版本树而非单一版本线（ADR-5）

用户可能说"这个方向不对，回到第 2 版的感觉，但候选栏用第 4 版的"。版本管理不是线性时间线，而支持：

- 每版可查看、可预览（复用 §4.7 版本化资源加载）
- 以某历史版本为基础**分叉**出新版本
- 把某历史版本的某个元素（如候选栏设计）**合并**进当前版本

这要求 A3 产出在结构上**可拆解、可局部替换**——反过来印证 §3.1"结构化、可追溯、可单独重跑"设计的必要性：没有这个地基，版本树/局部合并根本无法实现。

### 5.6 终止条件

用户明确表达满意（点击"确认此版本"）才进入定稿导出。系统不在无明确信号时自作主张判定"已改好"，也不在每轮生成后追问"还满意吗"打断体验——保持"生成 → 用户体验 → 用户主动决定是否继续提反馈"的自然节奏。界面始终清楚放着"确认使用这版"入口，但不强迫点。

### 6.2 关键交互原则（均由原则二推导）

**预览是主角，不是配角**：右侧预览占据视觉主导（不是缩略图角落），因为这是用户判断"这版行不行"的核心依据。版本切换、反馈输入都设计成**不打断预览可见性**——反馈输入区常驻底部而非弹窗遮挡预览。

**等待体验分出口如实呈现**：四个出口的生成耗时差异很大——搜狗 PC 快（纯程序化组装），百度 PC 因 GUI 自动化耗时更长且波动大，移动端两个出口耗时取决于 M0 确定的生成路径。前端**分别显示各出口生成进度**，哪个出口先好就先让用户在对应设备/厂商预览里体验，而非被迫等最慢的出口卡住所有体验。预览什么时候能看就什么时候展示，不为"统一步调"人为拖慢已完成的部分。

**移动端/桌面端预览切换是核心而非可选（ADR-8）**：本期同时覆盖 PC 与移动端，预览必须提供清晰的**"预览设备"切换（PC 虚拟键盘 vs 手机虚拟键盘）**，与"厂商切换（搜狗/百度）"组成二维矩阵，默认聚焦用户当前关注的出口。绝不能让用户混淆"现在看到的到底是哪个设备、哪个厂商的效果"。手机预览要真实到能体验九宫格、按键音效、按下动效、手势（见 §4.8），因为这些正是手机用户判断皮肤好不好用的核心依据（原则二）。

**反馈输入低门槛**：反馈框像聊天一样自然，不需要用户学习"如何正确提反馈"的规则，点选元素只是加分项。这样"细致地一轮轮指出问题"对用户门槛足够低。

**版本对比而非纯线性历史**：提供"并排对比两个版本"能力（左右分屏预览），符合"人在比较中做判断，不在孤立展示中做判断"的实际决策方式。

### 6.3 提示词优化对话的分寸

- 优先从已有素材（参考图/视频）推断，能推断的不问。
- 真正要问的，一次只问一个最关键的缺口（如"这套皮肤主要你自己日常用，还是想做成分享给别人、更有记忆点的风格？"——能显著收窄方向），不做问卷式连续追问。
- 用户随时可说"你看着办"跳过，此时基于已有信息给合理默认判断，并在 Design Brief 里注明"以下为智能体推断，非用户明确指定"，方便确认环节一眼看出需重点检查的推断内容。

## 7. 数据模型与状态

> 原文这块只有一句话。数据模型是版本树、局部重跑、局部合并的落地地基，此处补齐。

### 7.1 领域模型（实体关系）

```
Project (皮肤项目)
  ├─ id, name, owner, target_platforms[], created_at
  └─ 1..N ─▶ Version (版本，版本树节点)
                ├─ id, project_id, parent_version_id?（分叉来源，null=根）
                ├─ status: draft | generating | ready | confirmed | exported
                ├─ 1 ─▶ DesignBrief   （A1 产出，可编辑）
                ├─ 1 ─▶ VisualSpec     （A2 产出：设计 token + 设计稿引用）
                ├─ 1 ─▶ AssetBundle    （A3 产出）
                │         ├─ design_layer（平台无关：主视觉/色板/字体/动效脚本/音效方案）
                │         └─ platform_layer{               // 厂商 × 设备 四象限
                │              sogou_pc, sogou_mobile,
                │              baidu_pc, baidu_mobile       // 每象限 = AssetSet
                │            }
                ├─ 0..N ─▶ PackageArtifact（A4 产出：.ssf/.bps/移动包 + 校验状态）
                ├─ 1 ─▶ QAReport        （A6 产出）
                └─ 0..N ─▶ Feedback     （本版收到的反馈）
                              ├─ type: asset_param | layout | style | platform | interaction
                              ├─ input_mode: free_text | element_pick
                              ├─ target_node_id?（点选/解析定位到的 token/资产 ID）
                              └─ resulting_version_id?（该反馈驱动生成的新版本）

SatisfactionMark（"已确认满意"标记，跨版本）
  └─ version_id, element_id, source: explicit | inferred_two_rounds_silent

PlatformKnowledgeBase（平台格式知识库，全局）
  ├─ sogou_skin_ini_field_dict（真实样本归纳的字段字典）
  ├─ baidu_editor_ui_map（自动化控件树映射 + 版本）
  └─ compatibility_table（客户端 min/max 版本兼容）
```

**设计要点**：

- `Version.parent_version_id` 使版本天然成树（非线性历史），支撑 §5.5 分叉。
- `AssetBundle` 显式分 `design_layer` / `platform_layer`（**厂商 × 设备 四象限**），落地 §2.3 复用策略与"单个象限重跑不影响其余象限"。
- 移动象限的 `AssetSet` 额外含 PC 象限没有的资产类型：**九宫格/全键盘两套布局切图、按键音效文件、按下/弹跳动效帧、手势反馈资产、多 DPI 档位切图**；`element_id` 命名空间需覆盖这些新类型。
- `AssetSet` 内元素带稳定 `element_id`，是局部合并、局部重跑、元素级满意标记、点选反馈定位的**共同锚点**。
- 一切产出带 `provenance`（输入哈希 + 依赖版本），支撑增量重跑缓存命中。

### 7.2 DesignBrief 结构示例

```json
{
  "style_keywords": ["国潮", "水墨", "留白"],
  "color_palette": { "primary": "#...", "accent": "#...", "background": "#..." },
  "mood": "沉静内敛",
  "material_direction": "哑光纸质感，非玻璃拟态",
  "corner_radius_preference": "large",
  "motion_intent": ["候选词切换有淡入效果"],
  "reference_assets": { "image": "...", "video_keyframes": ["..."] },
  "ambiguity_resolved_by": ["用户回答的追问", "参考图推断"],
  "inferred_fields": ["material_direction", "corner_radius_preference"]
}
```

`inferred_fields` 标注哪些字段是智能体推断而非用户明确指定，前端在确认卡片上高亮，落地 §6.3。

### 7.3 状态与偏好学习

- **用户反馈日志**：同项目内记录每轮反馈及其路由结果，供 A1/A2 学习偏好，减少同一问题重复犯错。
- **偏好不跨项目污染**：默认偏好学习限本项目内；跨项目复用需用户显式授权（避免"上个项目的冷淡风格"污染这个"活泼风格"项目）。

## 9. 非功能性设计

> 原文散落若干性能/体验期望，此处集中为可度量的约束。

### 9.1 性能与体验预算

| 指标 | 目标 | 依据 |
|---|---|---|
| 预览按键→候选词呈现延迟 | ≤ 50ms（跟手无感），PC 与移动九宫格/全键盘同标准 | §4.3/§4.8 不能破坏真实感 |
| 移动预览按键音效延迟 | ≤ 30ms（听感与按下同步） | §4.8 音效是移动皮肤核心卖点 |
| 移动预览按下动效帧率 | ≥ 50fps（无卡顿） | §4.8 弹跳/波纹动效跟手 |
| 历史版本预览切换 | ≤ 1s（秒级） | §4.7 版本化资源加载 |
| 搜狗PC端首版生成 | 目标数十秒级，进度实时 | §2.1 纯程序化 |
| 各出口生成 | 耗时差异大，**分出口独立进度如实呈现**，快的不被慢的拖慢 | §2.2 / §6.2 |
| 局部反馈重跑 | 只重跑受影响节点，远快于整体重生成 | §5.3 |

### 9.2 可用性与容错

- 百度自动化任一环节失败 → 明确报告"卡在哪一步"，绝不静默产出假文件（§2.2）。
- 自动化不稳时进人工监督队列兜底，用户侧体验不变（§2.2 降级路径）。
- QA 失败先自动修正，仅自动修正也失败才暴露给用户（§3.4）。

### 9.3 可扩展性

- 新增平台（如第三家输入法）= 新增一组 Platform Adapter（按需 PC/移动）+ 一套预览交互逻辑，不动设计层与编排层（§2.3 分层收益）。
- 设备维度已是一等公民：PC 与移动共享设计层与预览基座，交互层与适配层各自独立，新增设备形态（如平板）沿同一模式扩展（§4.8）。

### 9.4 安全、合规与成本

- **来源可信度**：百度编辑器二进制须来自官方渠道，不依赖论坛/网盘镜像（§11.1）；批量使用可能需与百度商务沟通授权。
- **版权**：不绕过平台版权保护机制盗取他人皮肤素材；生成资产的版权归属需明确。
- **成本可观测**：图像生成、沙箱池是主要成本项，需按项目/版本计量，避免无谓整体重跑（§5.3 也是成本优化）。

## 10. 质量保障与回归测试

- **搜狗**：建立"生成 → 真机验证"自动化回归集，覆盖不同分辨率/DPI，用真实客户端验证安装与显示。
- **百度**：建立自动化脚本对"编辑器当前版本"的回归集；编辑器升级时先跑回归再上线。
- **预览引擎**：用真实测试语料验证拼音引擎"常用词覆盖率"，避免"常用词打不出来"破坏预览可信度（§11.3）。
- **长期兼容**：四出口对应的客户端升级都可能让历史皮肤失效，需长期"监测 + 回归"机制，纳入路线图（§11.4）。

## 11. 风险登记与技术验证

把"尚未证实、需真实环境测试才能确认"的部分明确列出，不混进"已确定可行"的部分，避免团队基于乐观假设排期。

### 11.1 P0：百度编辑器自动化可行性 Spike

**风险**：整个百度 PC 出口（`.bps` 真实安装包）的可行性系于此，是**可能导致百度 PC 出口方案调整**（回退降级路径甚至重议该出口范围）的风险。与 §11.5 移动端格式调研并列为 M0 两大 P0 验证项。

**需验证的具体问题**：

1. BDPYSkinEditor 官方正式下载渠道（须官方页面直接下载，非论坛/网盘镜像；涉及来源可信度与批量使用授权，可能需商务沟通）。
2. 编辑器是否需登录/联网校验才能新建工程、导入素材、导出（若导出强制联网校验且有频率限制，无人值守批量会受限）。
3. UI 控件是否有可访问性标识（Windows UIAutomation 树能否稳定识别每个按钮/输入框），还是纯自绘只能像素定位（后者显著提高脆弱性与维护成本）。
4. 是否支持导入工程文件实现"预填参数一键导出"，还是每次必须从新建工程走完整流程（后者环节多、出错概率高）。
5. "检错"结果是否程序可读（状态栏/弹窗文字），能否被脚本读取用于判断重试。

**验证方式**：搭独立 Windows 沙箱，装编辑器，人工先走完整流程记录每步界面结构，再用 pywinauto 逐步替换人工点击，记录哪些步骤能稳定自动化、哪些不能，产出"自动化可行性评估报告"，据此决定人工监督兜底方案及其触发比例。

### 11.2 P1：搜狗 skin.ini 完整字段核实

搜狗路径整体可行性高，但 `skin.ini` **完整**字段列表（尤其影响体验的不常用字段，如 apng 帧率控制、拉伸区精确语法）须用真实样本核实，不能只靠搜索摘要碎片。**做法**：下载数十个真实上架搜狗皮肤，批量改名解压，做字段频率统计与语法归纳，作为 A4 权威**参数字典**来源——比只读官方教程 PDF 更全（教程可能只覆盖基础用法，作者摸索的进阶用法常没写进官方文档）。

### 11.3 P1：预览引擎拼音引擎选型

评估候选开源词库/分词方案在"响应速度"和"日常词汇覆盖率"间的平衡，用真实测试语料跑一遍，确认不出现明显"常用词打不出来"破坏预览可信度。

### 11.4 P2：版本兼容性长期维护

搜狗侧确认存在版本兼容标记（min/max）；百度侧大概率类似；移动端各平台机制待 M0 确认。四出口对应的客户端升级都可能让历史皮肤失效或显示异常，需长期"监测 + 回归测试"机制，不是一次性生成完就不管。非初期架构必须解决，但需在路线图占位，避免上线后被动。

### 11.5 P0：移动端皮肤格式与生成路径第一轮调研

**风险**：移动端是本期硬需求，但搜狗移动、百度移动皮肤的格式与生成路径**尚无第一轮调研的事实基础**（不像 PC 端已有确认事实）。在事实到位前，移动端两个出口的适配层策略无法定型。与 §11.1 并列为 M0 两大 P0 验证项。

**需验证的具体问题（每项区分"已确认/需验证"，不搜到的如实标注）**：

1. 搜狗移动、百度移动皮肤各自的**文件格式**（后缀、是否 zip 家族、是否签名/加密）；与各自 PC 格式的差异。
2. 内部结构：配置文件形态（JSON/XML/私有）、包含哪些资源（含音效/动效资源如何组织）。
3. 官方是否提供**皮肤 DIY 工具**（App 内置 / 网页版 / 设计规范），产物能否被程序化生成或工具能否被自动化驱动。
4. **能否编程直生**（落到 §0 原则首选档），还是必须驱动官方工具（落到驱动 + 人工兜底档）。
5. 各平台移动端**可自定义能力清单**：九宫格/全键盘布局、按键音效、振动、按下动效、手势/滑行输入、（百度）自定义按键功能等超视觉能力——决定 Design Brief / Visual Spec 需建模到多细。
6. **多机型 DPI 适配**要求与资源密度档位。
7. **Android / iOS 差异**：格式或机制是否分叉；iOS 沙箱是否带来额外约束。
8. 是否需**账号登录/联网校验**才能制作或使用皮肤（影响无人值守批量生成，与百度 PC 自动化风险同源）。

**验证方式**：检索官方文档/设计规范 + 下载真实移动皮肤样本改后缀解压研究 + 若有 DIY 工具则人工走一遍完整流程记录结构。产出"移动端格式与生成路径评估报告"，据此为搜狗移动、百度移动各自选定生成路径档位，并回填 §2.4/§2.5、§8 移动适配行、里程碑。

**第一轮调研进展（2026-07，WebSearch 摘要级 → 部分工具源码确证）**：

> 已完成第一轮调研并回填 §2.4/§2.5（分级）。**搜狗移动**（摘要级）：`.ssf`(zip+skin.ini，与 PC 同族)、官方有尺寸标注页。**百度移动**：先摘要级(后缀分化 `.bdi`/`.bds`/`.bps`、Land/Port/Res)，后经**开源生成器 BGtool.c 源码确证**布局格式——`[INPUT]/[CAND]/[PANEL]/[KEY n]` 段 + `VIEW_RECT/TOUCH_RECT/BACK_STYLE` + 手势键 `CENTER/HOLD/HOLDSYM/UP/DOWN/LEFT/RIGHT` + `.til` 切片(`SOURCE_RECT`) + STYLE 样式(`NM_IMG/HL_IMG`)。**关键分叉**：`.bdi/.bds`(可编程直生) vs `.bps`(需驱动工具)。
>
> **仍缺权威级（需真机/官方样本）**：当前主流版本接受的后缀、`.bps` 是否强制、颜色/尺寸取值编码、是否需登录校验、iOS/Android 差异、真机安装。开源旁证：`github.com/fkxxyz/ssfconv`(搜狗，已用于确证 skin.ini 字段)、`github.com/Gearkey/baidu_input_skins`(百度，含 BGtool.c 源码与真实 .bds 样本)。
> - 若持续 429，改用带独立网络出口的抓取通道，或人工下载样本离线分析。

### 11.6 P1：移动端九宫格 T9 拼音方案选型

预览的移动运行时需真实九宫格(9键 T9)输入。初步判断（待核验）：**无大厂官方开源的"手机 T9 成品引擎"**；主流可行路径是"开源 26 键拼音内核（librime / libpinyin / AOSP Pinyin 等）+ 自建 T9 数字→字母集合展开层 + 音节切分 + 词频/语言模型"，其中 **RIME 生态（librime / Trime）最易落地九宫格布局**。需 Spike 核验：① 可用的 RIME 九宫格/T9 方案仓库地址与维护状态；② 内核在响应速度与覆盖率上的实测表现（T9 歧义度高于 26 键，更依赖词库与排序，需单列验证）。**注意**：结巴仅分词、非 IME；`pypinyin`（汉字→拼音）可用于离线构建 T9 词典。所有开源仓库地址需上线前复核。

### 11.7 风险优先级与建议顺序

1. **M0 并列先做两大 P0 研究**：§11.1（百度 PC 自动化 Spike）与 §11.5（移动端格式与生成路径调研）——二者是唯二可能推翻对应出口方案的风险，越早验证越好。
2. 并行推进搜狗 PC 全链路（§11.2）和预览引擎（§11.3、§11.6 T9）——几乎不依赖上述两项研究的结论，可独立往前走。
3. §11.4 纳入长期运营计划，不阻塞首版上线。
